## 1. Введение

### 1.1. Назначение документа

Настоящий документ содержит полное техническое описание системы управления корпоративным менторством **«Менторинг»**. Документ предназначен для команды разработки и содержит все необходимые артефакты для реализации MVP-версии продукта.

### 1.2. Краткое описание системы

Система «Менторинг» автоматизирует процесс подбора менторов, управления менторскими парами, фиксации встреч и сбора обратной связи. Система интегрируется с существующей ERP-платформой компании.

### 1.3. Целевая аудитория

| Роль | Описание |
|------|----------|
| **HR-менеджер** | Управляет программой менторства, назначает пары, контролирует процесс |
| **Ментор** | Опытный сотрудник, передающий знания и навыки |
| **Менти (ученик)** | Новый или развивающийся сотрудник, которому нужен наставник |

## 2. Бизнес-контекст и цели

### 2.1. Проблема

В компании отсутствует единая система управления менторством:
- Нет базы менторов и их компетенций
- Назначение ментора происходит вручную
- Прогресс не отслеживается
- Результаты не фиксируются и не анализируются

### 2.2. Бизнес-цели

| № | Цель | Измеримый результат |
|---|------|---------------------|
| 1 | Автоматизировать подбор менторов | Система предлагает ментора по компетенциям |
| 2 | Отслеживать прогресс | Журнал встреч и обратная связь |
| 3 | Сделать программу прозрачной | Дашборд для HR со статистикой |

### 2.3. Бизнес-ценность

- 📈 **Сокращение времени адаптации** новых сотрудников на 20-30%
- 🧠 **Снижение риска ухода знаний** при увольнении ключевых специалистов
- 🎯 **Повышение вовлечённости** и лояльности сотрудников
- 📊 **Прозрачность инвестиций** в развитие персонала

## 3. Границы проекта

### ✅ Входит в MVP

- Регистрация в программе (как ментор или менти)

- Мобильное приложение

## 4. Бизнес-процессы (BPMN)

### 4.1. Основной процесс: "Подбор ментора"

Процесс начинается с того, что сотрудник подаёт заявку на участие в программе менторства. Далее система проверяет, есть ли у сотрудника уже активный ментор (чтобы избежать дублирования). Если ментор уже есть — процесс завершается. Если нет — система ищет подходящих кандидатов на основе компетенций. HR получает список и утверждает одного из кандидатов. Ментор подтверждает участие, и пара создаётся. Процесс завершается уведомлением менти о назначении ментора.

### 4.2. Участники процесса (Pools)

| Пул | Участник | Описание |
|-----|----------|----------|
| **Pool 1** | Сотрудник (Менти) | Подаёт заявку, получает уведомление |
| **Pool 2** | Система | Автоматический поиск кандидатов |
| **Pool 3** | HR-менеджер | Утверждает кандидата |
| **Pool 4** | Ментор | Подтверждает участие |

## 6. Функциональные требования

### 6.1. Требования к пользовательским ролям

| ID | Требование | Приоритет |
|----|------------|-----------|
| FR-1 | Система должна поддерживать 4 роли: HR, Ментор, Менти, Администратор | Высокий |
| FR-2 | HR должен иметь доступ к дашборду со статистикой | Высокий |
| FR-3 | Ментор должен иметь доступ к своим заявкам и журналу встреч | Высокий |
| FR-4 | Менти должен иметь доступ к своему журналу встреч и форме создания заявки | Высокий |

### 6.2. Требования к заявкам на менторство

| ID | Требование | Приоритет |
|----|------------|-----------|
| FR-5 | Менти может создать заявку с указанием списка компетенций | Высокий |
| FR-6 | Система должна автоматически находить кандидатов в менторы по компетенциям | Высокий |
| FR-7 | HR может вручную назначить ментора из списка кандидатов | Высокий |
| FR-8 | Ментор может принять или отклонить заявку | Высокий |

### 6.3. Требования к менторским парам

| ID | Требование | Приоритет |
|----|------------|-----------|
| FR-9 | Система создаёт пару «ментор-менти» при одобрении заявки | Высокий |
| FR-10 | Пара имеет статусы: «Активна», «Закрыта» | Средний |
| FR-11 | HR может просматривать все активные пары на дашборде | Высокий |

### 6.4. Требования к журналу встреч

| ID | Требование | Приоритет |
|----|------------|-----------|

## 8. Модель данных (ER-диаграмма)

### 8.1. Описание сущностей

| Сущность | Описание |
|----------|----------|
| **User** | Сотрудник компании |
| **Mentor** | Профиль ментора (связь 1:1 с User) |
| **Competency** | Компетенция (навык) |
| **MentorCompetency** | Связь ментора с компетенцией (с уровнем владения) |
| **Request** | Заявка на менторство |
| **MentoringPair** | Пара «ментор-менти» |
| **Meeting** | Встреча менторской пары |

### 8.2. Схема данных

> 📎 **Артефакт:** [`diagrams/ER-diagram.png`](./diagrams/ER-diagram.png)

### 8.3. Описание связей

| От | К | Тип | Описание |
|----|---|-----|----------|
| User | Mentor | 1:1 | У каждого пользователя может быть 0 или 1 профиль ментора |
| Mentor | MentoringPair | 1:M | Один ментор может иметь много пар |
| User (mentee) | MentoringPair | 1:M | Один менти может иметь много пар (но только 1 активную) |
| Mentor | MentorCompetency | 1:M | Один ментор может иметь много компетенций |
| Competency | MentorCompetency | 1:M | Одна компетенция может быть у многих менторов |
| MentoringPair | Meeting | 1:M | Одна пара может иметь много встреч |
| User | Request | 1:M | Один пользователь может создать много заявок |
| Mentor | Request | 1:M | Ментору может быть назначено много заявок |
| Request | MentoringPair | 1:1 | По одной заявке создаётся одна пара |

### 8.4. Статусы

**Request_status:**
1. `created` — Создана (HR может назначить ментора)
2. `under_review` — На рассмотрении (ментор просматривает)
3. `approved` — Одобрена (создаётся пара)
4. `rejected` — Отклонена

**MentoringPair_status:**
1. `active` — Активна
2. `closed` — Закрыта

## 9. API-спецификация

### 9.1. Общая информация

| Параметр | Значение |
|----------|----------|
| **Базовый URL** | `https://api.mentoring.company.com/v1` |
| **Формат данных** | JSON |
| **Кодировка** | UTF-8 |
| **Авторизация** | JWT (Bearer Token) |

### 9.2. Список эндпоинтов

| Группа | Метод | Эндпоинт | Описание |
|--------|-------|----------|----------|
| **Users** | GET | `/users` | Список пользователей |
| | GET | `/users/{id}` | Пользователь по ID |
| | POST | `/users` | Создать пользователя |
| | PUT | `/users/{id}` | Обновить пользователя |
| **Mentors** | GET | `/mentors` | Список менторов |
| | GET | `/mentors/{id}` | Ментор по ID |
| | POST | `/mentors` | Создать профиль ментора |
| | PUT | `/mentors/{id}` | Обновить профиль |
| **Competencies** | GET | `/competencies` | Список компетенций |
| | POST | `/competencies` | Создать компетенцию |
| | DELETE | `/competencies/{id}` | Удалить компетенцию |
| **Requests** | GET | `/requests` | Список заявок |
| | POST | `/requests` | Создать заявку |
| | PUT | `/requests/{id}/status` | Изменить статус |
| **Pairs** | GET | `/pairs` | Список пар |
| | GET | `/pairs/{id}` | Пара по ID |
| | PUT | `/pairs/{id}` | Обновить статус пары |
| **Meetings** | GET | `/meetings` | Список встреч |
| | POST | `/meetings` | Создать встречу |
| | PUT | `/meetings/{id}` | Обновить встречу |

### 9.3. Примеры запросов

**Создание заявки на менторство:**

```http
POST /requests
Content-Type: application/json

{
  "user_id": 10,
  "competency_list": "Java, Spring, SQL"
}
```

**Ответ:**

```json
{
  "id": 1,
  "user_id": 10,
  "status": "created",
  "competency_list": "Java, Spring, SQL",
  "created_at": "2026-08-30T10:00:00Z"
}
```

**Изменение статуса заявки (HR назначает ментора):**

```http
PUT /requests/1/status
Content-Type: application/json

{
  "status": "under_review",
  "mentor_id": 5
}
```

### 10.2. Описание ключевых экранов

#### 10.2.1. HR / Подбор ментора ([`figma_png/01_hr_req.png`](./figma_png/01_hr_req.png))

**Назначение:** Управление заявками и подбор менторов.

**Ключевые элементы:**
- Список заявок сотрудников (имя, должность, компетенции)

**Сценарий использования:**
1. HR видит список сотрудников, подавших заявку
2. Для каждого сотрудника система показывает подходящих кандидатов
3. HR выбирает кандидата и нажимает «Отправить приглашение»

#### 10.2.2. HR / Дашборд ([`figma_png/02_hr_dashboard.png`](./figma_png/02_hr_dashboard.png))

**Назначение:** Обзор всех активных процессов.

**Ключевые элементы:**
- Карточки KPI: Всего пар, Активных, Завершённых, Рейтинг
- График динамики пар
- Список активных пар с датами
- Календарь встреч

**Сценарий использования:**
1. HR заходит на дашборд и видит общую статистику

#### 10.2.3. Ментор / Профиль и заявки ([`figma_png/03_mentor_req.png`](./figma_png/03_mentor_req.png))

**Сценарий использования:**
1. Ментор видит свои компетенции и может их редактировать
2. Получает уведомление о новых заявках
3. Принимает или отклоняет заявку

#### 10.2.4. Ментор / Журнал встреч ([`figma_png/04_mentor_log.png`](./figma_png/04_mentor_log.png))

**Сценарий использования:**

2. Заполняет форму: дата, менти, оценка (1-5), комментарий

**Сценарий использования:**

2. Оставляет оценку и комментарий о встрече

#### 10.2.6. Менти / Создание заявки ([`figma_png/06_empl_req.png`](./figma_png/06_empl_req.png))

**Сценарий использования:**
1. Менти вводит компетенции, которые хочет изучить
2. Нажимает «Create a mentoring request»
3. Заявка отправляется на рассмотрение HR

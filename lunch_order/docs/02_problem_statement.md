## 1. Общее описание

Модуль «Заказ обедов» — самостоятельный модуль, который подключается к корпоративному веб-порталу компании. Модуль позволяет сотрудникам заказывать обеды из меню одной или нескольких столовых, а администратору — управлять справочниками, меню, заказами, отчётами, пользователями и настройками модуля.

**Заказчик:** компания, владеющая корпоративным порталом, которая хочет организовать питание сотрудников через несколько столовых.

**Режимы работы модуля:**
1. **В составе корпоративного портала** — рабочее приложение. Аутентификацию обеспечивает портал. Из портала приходят: список всех пользователей (ID, ФИО, роль) и информация о текущем пользователе (ID, ФИО, роль). Назначение ролей внутри модуля — через форму «Управление пользователями».
2. **В составе демо-портала** — демонстрационное приложение. Полноценная аутентификация не используется, гость определяется по IP-адресу, информация о нём создаётся в БД.

**Нагрузка:** до 5 000 зарегистрированных пользователей. Поддержка современных браузеров (Edge, Chrome, Yandex, Safari, Firefox и другие популярные).

**Развёртывание:** на серверах заказчика, с использованием Docker. Специальных требований к CI/CD нет.

## 2. Роли

Всего в модуле **5 ролей**. Роль **Супер-администратор** является **сквозной**: активна и в корпоративном, и в демо-режиме, права одинаковые.

### 2.1. Группа 1. Роли корпоративного портала
- **Сотрудник** — заказывает обеды, просматривает свои заказы, редактирует профиль.
- **Администратор** — управляет справочниками и меню, заводит заказы за сотрудников, формирует отчёты, управляет пользователями. Имеет персональные флаги (см. 2.4), которыми управляет Супер-администратор.
- **Супер-администратор** — полный доступ, включая управление Администраторами и Супер-администраторами, настройки модуля, демо-функции.

### 2.2. Группа 2. Роли демо-портала
- **Гость-Сотрудник** — то же, что Сотрудник, но в демо-режиме.
- **Гость-Администратор** — то же, что Администратор, но в демо-режиме; не может импортировать меню, управлять столовыми, очищать данные. Видит форму «Управление пользователями», но не редактирует её (только просмотр), и не видит там Супер-администраторов.
- **Супер-администратор** — то же, что в портале (сквозная роль).

### 2.3. Сквозная роль
- **Супер-администратор** — владелец модуля. Одинаковые права в обоих режимах.

### 2.4. Персональные флаги Администратора
Супер-администратор управляет персональным флагом каждого Администратора (в форме «Управление пользователями»):
- **«Может заказывать обед самому себе»** — вкл/выкл.

Других флагов нет.

### 2.5. Назначение ролей и идентификация Супер-администратора
- **Первый Супер-администратор** устанавливается SQL-запросом (флаг в таблице пользователей). Через интерфейс этот флаг установить нельзя. К модулю прилагается инструкция с SQL-запросом. Механизм одинаков для корпоративного и демо-режима.
- После установки первого Супер-администратора он может назначать других Супер-администраторов через форму «Управление пользователями».
- **Администратор** может назначать Администраторов и снимать права Администратора с других Администраторов. Не может назначать Супер-администраторов и не может назначить себя Супер-администратором.
- **Супер-администратор** может назначать Супер-администраторов и снимать права Супер-администратора с других пользователей, но **не с себя**.
- **Сотрудников** можно переводить в Администраторы и обратно.
- В демо-режиме: Гость-Администратор видит форму «Управление пользователями», но **не редактирует** её. Супер-администратор видит всех, включая себя, и управляет правами. В демо может быть несколько Супер-администраторов (если первый назначит других).

## 3. Границы

**Входит в объем работ:**
- Формы сотрудника: «Заказ обеда», «Мои заказы», «Профиль».
- Формы администратора: «Управление столовыми», «Управление меню», «Управление заказами», «Импорт меню», «Отчёты», «Управление пользователями».
- Форма «Управление модулем» — только Супер-администратор.
- Роли: Сотрудник, Администратор, Гость-Сотрудник, Гость-Администратор, Супер-администратор.
- Персональный флаг Администратора (1 флаг).
- Справочники: пользователи, столовые, наши категории позиций, подкатегории, категории столовых, позиции, меню, заказы.
- Статусы меню и заказов, связь между ними.
- Импорт меню из Excel: универсальный парсер с UI маппинга колонок; отдельный формат для каждой столовой + эталонный шаблон разработчика.
- **Ручное копирование меню** администратором (в демо и корпоративном режимах).
- **Подкатегории** внутри наших категорий: справочник, поле у позиции, сортировка (подкатегории → закреплённые → алфавит).
- Отчёты: по категориям столовой, по сотрудникам. Параметры отчёта, PDF на сервере, без истории.
- Демо-режим: гость по IP, переключение ролей, изоляция данных, скрипт копирования меню по расписанию.
- Очистка данных: только автоматическая, по заданному параметру `retention_days`.
- Настройки модуля: `retention_days`, расписание скрипта копирования меню (демо).
- Логирование работы скриптов (текстовые файлы в фиксированной директории на сервере).
- Интеграция с порталом: получение пользователей и текущего пользователя.

**Не входит в объем работ:**
- Оплата и биллинг (взаиморасчёты — через бухгалтерию).
- Уведомления (email/push/мессенджеры).
- Мобильное приложение (только веб).
- Интеграция с бухгалтерией и 1С.
- Рейтинг блюд.
- Архивирование данных (только удаление).
- Ручная очистка данных (только автоматическая по `retention_days`).
- Шаблоны экспорта отчётов.
- История сформированных отчётов.
- Логирование операций приложения (логируют только скрипты).
- Просмотр логов через интерфейс модуля.

## 4. Глоссарий

| Термин | Определение |
|--------|-------------|
| **Позиция** | Блюдо или напиток в справочнике позиций. |
| **Наша категория** | Одна из 5 фиксированных категорий: Салаты/Закуски/Бутерброды, Супы, Вторые блюда и гарниры, Десерты, Напитки. Используется для логики заказа и сортировки. |
| **Подкатегория** | Подраздел внутри нашей категории (например, «Салаты», «Закуски», «Бутерброды» внутри категории «Салаты/Закуски/Бутерброды»). Используется для сортировки в UI заказа. |
| **Категория столовой** | Категория, в которой позиция пришла от столовой. Используется в отчётах. |
| **Меню** | Запись в справочнике меню, привязанная к конкретной столовой и дате. Содержит набор позиций и статус. |
| **Заказ** | Запись в справочнике заказов: сотрудник + меню + состав позиций + статус. Один заказ = один обед на один день. |
| **Гарнир** | Позиция с флагом «Гарнир». Может быть выбрана в качестве второй части составного блюда. |
| **Составное блюдо** | Позиция с флагом «Требует гарнира», к которой сотрудник выбирает вторую часть (гарнир или «Гарнир не нужен»). Максимум две части. |
| **Статус меню** | «В разработке», «Открыто для заказов», «Закрыто для заказов». |
| **Статус заказа** | «Обед не нужен», «Открыт для редактирования», «Отменён», «Закрыт для редактирования». |
| **Персональный флаг** | Настройка Администратора, которой управляет Супер-администратор. |
| **`retention_days`** | Срок хранения данных о меню и заказах (дней от текущей даты). Одно значение на весь модуль. |

## 5. Справочники и структура данных

В каждый справочник добавляются служебные поля: дата создания, дата модификации, идентификатор пользователя, создавшего запись.

### 5.1. Справочник пользователей
Единая сущность для сотрудников, администраторов, супер-администраторов и гостей демо.

Поля: ID, ФИО (имя), роль, внешний идентификатор пользователя (строковое: IP в демо, ID платформы в портале), столовая по умолчанию, дата создания аккаунта, признак «системные данные» (`system_flag`), признак «не используется», флаг «Может заказывать обед самому себе», служебные поля.

### 5.2. Справочник столовых
Поля: ID, наименование, признак «не используется», служебные поля.

### 5.3. Справочник наших категорий позиций
Поля: ID, наименование, порядок вывода категорий, признак «не используется», служебные поля.

**5 категорий:** Салаты/Закуски/Бутерброды, Супы, Вторые блюда и гарниры, Десерты, Напитки.

### 5.4. Справочник подкатегорий
Отдельная сущность. Жёстко привязана к одной нашей категории. Заполняется вручную администратором.

Поля: ID, наименование, наша категория (одна на подкатегорию), порядок вывода подкатегорий внутри категории, признак «не используется», служебные поля.

### 5.5. Справочник категорий столовых
Отдельная сущность. Заполняется автоматически при парсинге файла столовой.

Поля: ID, наименование, привязка к столовой, признак «не используется», служебные поля.

### 5.6. Справочник позиций
Поля: ID, наименование (уникальное), **наша категория** (одна на позицию), **подкатегория** (может быть пустой), **категория столовой** (одна на позицию), вес блюда, цена, флаг «Требует гарнира», флаг «Гарнир», **порядок закрепления** (0 / пусто = не закреплена; 1, 2, 3… = закреплена, сортируется по возрастанию), признак «не используется», служебные поля.

**Бизнес-правила:**
- Наименование позиции уникально.
- Позиция с одинаковым названием не может быть в разных наших категориях.
- При импорте меню позиции автоматически создаются на основе уникальности названия.
- Сортировка в UI заказа: сначала по порядку подкатегорий, внутри подкатегории — сначала закреплённые (по порядку закрепления), затем незакреплённые (по алфавиту).
- Отчёты — по категориям столовой.

### 5.7. Справочник меню
Поля: ID, дата, столовая, статус (В разработке / Открыто для заказов / Закрыто для заказов), признак «не используется», служебные поля.

### 5.8. Справочник заказов
Поля: ID, сотрудник, меню, состав заказа, статус (Обед не нужен / Открыт для редактирования / Отменён / Закрыт для редактирования), служебные поля.

### 5.9. Таблица настроек модуля
Параметры: `retention_days` (одно значение на модуль), расписание скрипта копирования меню (демо).

## 6. Статусы и переходы

### 6.1. Статусы меню
1. **В разработке** — меню создаётся, сотрудникам недоступно.
2. **Открыто для заказов** — сотрудники могут заказывать.
3. **Закрыто для заказов** — заказы не принимаются.

### 6.2. Статусы заказа
1. **Обед не нужен** — пустой заказ, сотрудник явно сообщает, что не будет питаться в указанную дату.
2. **Открыт для редактирования** — заказ оформлен, можно изменить.
3. **Отменён** — сотрудник отменил заказ.
4. **Закрыт для редактирования** — заказ закрыт, изменения запрещены (кроме администратора).

### 6.3. Связь статусов
- При переводе меню в «Закрыто для заказов» все связанные заказы переходят в «Закрыт для редактирования».
- При обратном переводе меню в «Открыто для заказов» заказы, бывшие в статусе «Закрыт для редактирования», остаются закрытыми.
- Администратор может вручную менять статус любого заказа.

## 7. Функциональные требования

### 7.1. Заказ обеда сотрудником
- Сотрудник выбирает дату или диапазон дат, столовую (по умолчанию — из профиля), видит меню, выбирает позиции.
- Из каждой нашей основной категории — только одна позиция.
- Из категории «Вторые блюда и гарниры» — только одна позиция, которая может быть:
  - односоставной («Котлета куриная с гречкой»);
  - составной: первая часть с флагом «Требует гарнира» + вторая часть из позиций с флагом «Гарнир», либо «Гарнир не нужен».
- «Гарнир не нужен» — вариант по умолчанию, всегда сверху выпадающего списка.
- Максимум две части в составном блюде.
- Возможность заказать на неделю (по одному на день).
- Возможность дозаказать в середине недели (в т.ч. накануне), пока меню не закрыто.
- Возможность создать пустой заказ со статусом «Обед не нужен» на дату или диапазон дат (N заказов).
- Возможность отменить заказ (→ «Отменён») или перевести в «Обед не нужен».
- На конкретный день сотрудник может заказать обед только в одной столовой.
- Сортировка позиций в UI заказа: сначала по порядку подкатегорий, внутри подкатегории — сначала закреплённые (по порядку закрепления), затем незакреплённые (по алфавиту).

### 7.2. Заказ за сотрудника администратором
- Администратор может завести обед за любого сотрудника, изменить статус любого заказа.
- Администратор может заказать обед самому себе **только если** Супер-администратор включил ему флаг «Может заказывать обед самому себе».

### 7.3. Управление меню
- Импорт меню из Excel: универсальный парсер с **UI маппинга колонок**. Администратор добавляет столовую → добавляет формат (маппинг колонок) → загружает файл.
- Эталонный Excel-шаблон разрабатывается в рамках проекта и поставляется вместе с модулем (для случаев, когда файл столовой «битый»).
- Ручное создание меню: администратор переносит данные в эталонный шаблон и загружает.
- Правка данных меню после импорта на форме.
- Автоматическое создание позиций при импорте (по уникальности названия).
- Автоматическое заполнение **категории столовой** при парсинге.
- **Наша категория** и **подкатегория** заполняются вручную администратором после импорта.
- Сортировка категорий и подкатегорий: администратор задаёт порядок через стрелки вверх/вниз на форме.
- **Закрепление позиций**: администратор задаёт числовое поле «порядок закрепления» у позиции (0 / пусто = не закреплена; 1, 2, 3… = закреплена, сортируется по возрастанию).
- Статусы меню: В разработке / Открыто для заказов / Закрыто для заказов.
- **Ручное копирование меню**: администратор копирует меню одной столовой на одну дату целиком. Копия создаётся в статусе «В разработке». Доступно в демо и корпоративном режимах.

### 7.4. Отчёты
- Отчёт по позициям с группировкой по **категориям столовой** (количества, сумма по весу и деньгам).
- Отчёт по позициям с группировкой по сотрудникам (с использованием категорий столовой).
- Параметры отчёта: выбор типа отчёта, столовой, периода, категорий, сотрудников.
- Кнопка «Выполнить запрос» → сформированный PDF открывается в отдельном окне.
- PDF формируется на сервере.
- История сформированных отчётов не сохраняется.

### 7.5. Управление пользователями
- Форма доступна Администратору, Гостю-Администратору (только просмотр) и Супер-администратору.
- Список пользователей с правами и персональным флагом.
- Администратор может назначать Администраторов и снимать права Администратора с других Администраторов. Не может назначать Супер-администраторов и не может назначить себя Супер-администратором.
- Супер-администратор может назначать Супер-администраторов и снимать права Супер-администратора с других пользователей, но не с себя.
- Сотрудников можно переводить в Администраторы и обратно.
- Супер-администратор управляет персональным флагом Администратора: «Может заказывать обед самому себе».
- В демо-режиме: Гость-Администратор видит форму, но не редактирует её; не видит Супер-администраторов. Супер-администратор видит всех, включая себя.

### 7.6. Управление модулем
- Форма доступна только Супер-администратору.
- Настройки: `retention_days` (одно значение на модуль), расписание скрипта копирования меню (демо).

### 7.7. Очистка данных
- Только автоматическая: скрипт (часть backend-приложения, cron внутри приложения) удаляет меню и заказы старше `retention_days`.
- Настройка `retention_days` — только Супер-администратор (в форме «Управление модулем»).
- Ручная очистка не предусмотрена.
- Работа скрипта логируется (см. п. 7.10).

### 7.8. Разграничение прав доступа
- Сотрудник: формы «Заказ обеда», «Мои заказы», «Профиль».
- Администратор: все формы, кроме «Управление модулем».
- Гость-Администратор: все формы, кроме «Управление модулем»; «Управление пользователями» — только просмотр; не может импортировать меню, управлять столовыми, очищать данные.
- Супер-администратор: все формы.

### 7.9. Демо-режим
- Гость попадает в модуль по ссылке, определяется по IP-адресу. Имя по умолчанию — «Гость».
- По умолчанию — роль «Гость-Администратор».
- Переключение ролей — в форме «Профиль»: Гость-Администратор / Гость-Сотрудник.
- «Выставить настройки профиля по умолчанию»: имя → «Гость», роль → «Гость-Администратор». Только в форме «Профиль».
- Изоляция данных: гость видит только системные данные и свои записи. Чужие записи не видны и не редактируются.
- Скрипт копирования меню (демо): командный файл на сервере, работает напрямую с БД, запускается по расписанию; каждую пятницу копирует меню 7-дневной давности на предстоящую неделю для всех столовых; если меню на дату уже есть — пропускает. Скопированные меню — статус **«Открыто для заказов»** (чтобы гости могли тестировать заказ без ручного вмешательства).
- Наполнение демо — через штатные формы («Управление столовыми», «Управление меню») Супер-администратором.
- Первый Супер-администратор в демо устанавливается SQL-запросом (тот же механизм, что в корпоративном режиме). Далее может назначать других.

### 7.10. Логирование работы скриптов
- Скрипты (копирование меню в демо, очистка данных) пишут логи в текстовые файлы в специальной директории на сервере.
- Путь к директории фиксированный, описан в инструкции по развёртыванию.
- Формат логов свободный.
- Просмотр логов через интерфейс модуля не предусмотрен; доступ — напрямую к директории на сервере.

## 8. Перечень форм

1. **«Заказ обеда»** — сотрудник.
2. **«Мои заказы»** — сотрудник.
3. **«Профиль»** — сотрудник, администратор, гость (переключение роли, сброс данных — только здесь).
4. **«Управление столовыми»** — администратор.
5. **«Управление меню»** — администратор (включая ручное копирование меню).
6. **«Управление заказами»** — администратор.
7. **«Импорт меню»** — администратор (включая UI маппинга колонок).
8. **«Отчёты»** — администратор.
9. **«Управление пользователями»** — администратор, гость-администратор (просмотр), супер-администратор.
10. **«Управление модулем»** — только супер-администратор.

## 9. Интеграция с внешним источником

- Из корпоративного портала приходят: список всех пользователей (ID, ФИО, роль) и информация о текущем пользователе (ID, ФИО, роль).
- Справочник столовых, меню, заказы — внутренние данные модуля.
- Поле «Внешний идентификатор пользователя» — строковое; в демо — IP-адрес, в портале — ID платформы.
- Маппинг ролей портала в роли модуля определяется на этапе внедрения для каждой компании. По умолчанию — «сотрудник»; роль «администратор» назначается по согласованию с компанией.
- Назначение ролей внутри модуля — через форму «Управление пользователями».
- Первый Супер-администратор устанавливается SQL-запросом; к модулю прилагается инструкция. Механизм одинаков для корпоративного и демо-режима.
- В демо-режиме полноценная аутентификация не используется; документация к демо-API разрабатывается в рамках проекта.
- Документация к API корпоративного портала предоставляется заказчиком на этапе внедрения.

## 11. Нефункциональные требования

- Аутентификация/авторизация: в корпоративном портале — на стороне портала; в демо — по IP-адресу.
- Логирование операций приложения не ведётся. Скрипты (копирование меню, очистка данных) пишут логи в текстовые файлы в специальной директории на сервере (см. п. 7.10).
- Валидация импортируемых файлов (формат, обязательные поля, дубли).
- Обработка ошибок импорта с подсветкой проблемных строк.
- Резервное копирование БД — на стороне инфраструктуры заказчика.
- Нагрузка: до 5 000 зарегистрированных пользователей.
- Браузеры: современные (Edge, Chrome, Yandex, Safari, Firefox и другие популярные).

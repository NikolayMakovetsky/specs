# ЗАЯВКА НА РАЗРАБОТКУ

---

## 1. Обоснование необходимости

1.1. Компания организует питание сотрудников через несколько столовых по договорам. Сотрудники должны выбирать заведение и блюда на дату, а компания — видеть спрос для ротации заведений.

1.2. Сейчас процесс ручной: заведения присылают меню администратору по email (сканы, фото), администратор рассылает их сотрудникам, те отвечают письмами, администратор вручную агрегирует заказы, звонит для уточнений и передаёт сводки заведениям.

1.3. Проблемы: высокая трудоёмкость, ошибки, нет единого формата меню, нет истории и аналитики, сотрудники ограничены в выборе.

1.4. Нужен модуль, который даст сотрудникам единый интерфейс заказа, снимет с администратора рутину и соберёт историю заказов.

---

## 2. Запрос

2.1. **Основные требования**
- 2.1.1. Модуль подключается к корпоративному порталу; работает в рабочем и демо-режимах.
- 2.1.2. Роли: Сотрудник, Администратор, Супер-администратор (сквозная), Гость-Сотрудник, Гость-Администратор.
- 2.1.3. Сотрудник видит доступные столовые и меню на дату, оформляет заказ.
- 2.1.4. Администратор управляет справочниками, меню, заказами, пользователями; формирует отчёты.
- 2.1.5. Супер-администратор управляет администраторами, настройками модуля, демо-функциями.
- 2.1.6. Импорт меню из Excel: универсальный парсер с настройкой маппинга колонок; отдельный формат для каждой столовой + эталонный шаблон.
- 2.1.7. Отчёты по категориям столовой и по сотрудникам; PDF на сервере.
- 2.1.8. Автоматическая очистка данных по `retention_days` (настраивает Супер-администратор).

2.2. **Описание процесса**
- 2.2.1. Администратор загружает меню от заведения через форму «Импорт меню».
- 2.2.2. Система парсит файл, создаёт позиции и категории столовой.
- 2.2.3. Администратор правит данные и переводит меню в «Открыто для заказов».
- 2.2.4. Сотрудник выбирает дату и столовую, оформляет заказ.
- 2.2.5. Администратор может завести заказ за сотрудника и изменить статус.
- 2.2.6. По завершении приёма заказов администратор закрывает меню.
- 2.2.7. Администратор формирует отчёты и экспортирует их в PDF.

2.3. **Что нужно сделать**
- 2.3.1. Веб-модуль на стеке PostgreSQL, .NET Core (C#), Vue.js; Docker на серверах заказчика.
- 2.3.2. Формы, справочники, импорт с UI маппинга, отчёты с PDF.
- 2.3.3. Демо-режим: гость по IP, переключение ролей, изоляция данных, скрипт копирования меню.
- 2.3.4. Автоматическая очистка данных и логирование работы скриптов.
- 2.3.5. Инструкция по развёртыванию и SQL-запрос для первого Супер-администратора.
- 2.3.6. Дизайн форм — в Figma.

2.4. **Образ результата**
- 2.4.1. Работающий модуль на серверах заказчика с демо-стендом.
- 2.4.2. Единый интерфейс заказа для сотрудников и управления для администратора.
- 2.4.3. История заказов по заведениям для анализа.

2.5. **Ценность**
- 2.5.1. Сотрудник: разнообразие, быстрый заказ, без переписок.
- 2.5.2. Администратор: меньше рутины, единый формат, отчёты в один клик.
- 2.5.3. Бизнес: прозрачный спрос, основа для ротации заведений.

---

## 3. Ограничения и допущения

3.1. Оплата, биллинг, уведомления, мобильное приложение, интеграция с бухгалтерией и 1С — не входят в объём работ.

3.2. API корпоративного портала и примеры Excel от столовых предоставляет заказчик.

3.3. Один сотрудник может заказать обед только в одной столовой на конкретный день.

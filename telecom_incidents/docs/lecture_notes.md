# Конспект обучающего видео по Camunda Modeller и TTM

## Введение

- **Цель видео**: Обучить работе с Camunda Modeller для настройки бизнес-процессов в системе Trouble Ticket Management (TTM).
- **Инструменты**:
    - **Camunda Modeller**: Платформа для моделирования BPMN-процессов.
    - **DBeaver**: Инструмент для работы с базой данных (просмотр и правка таблиц).
    - **TTM Web-приложение**: Интерфейс для работы с инцидентами и заданиями.

- **Аудитория**: Сотрудники разных уровней подготовки, от новичков до опытных аналитиков.
- **Формат**: Лекция с демонстрацией экрана, ответами на вопросы в чате и последующими тестами.

## Часть 1: Основы настройки бизнес-процессов

### 1. Концепция бизнес-процесса в TTM

- Бизнес-процесс — это «скелет» системы, который определяет, как система переходит от одного задания к другому.
- В TTM это реализовано в виде диаграмм BPMN, которые управляют потоком работ по инциденту.

### 2. Доступ к настройке бизнес-процессов

- **Привилегии**: Доступ к настройке управляется через привилегии, роли и группы в базе данных.
- **Проверка доступа**: В интерфейсе TTM нужно перейти во вкладку **Администрирование → Бизнес-процессы**. Если вкладка недоступна, значит, у пользователя нет прав.
- **Настройка прав**:
    1.  Найти необходимые привилегии в таблице `cat.privilege` (например, ID `41` и `30` для создания и редактирования).
    2.  Посмотреть, какая роль обладает этими привилегиями.
    3.  Добавить эту роль своему пользователю.

### 3. Интерфейс Camunda Modeller (Администрирование)

- **Список процессов**: Отображает все активные бизнес-процессы. Важно обращать внимание на пагинацию (процессы могут быть на второй странице).
- **Поиск**: Работает по частичному совпадению с именем процесса.
- **Просмотр схемы**: При открытии схемы можно управлять масштабом (`Ctrl` + колесико мыши) и перемещаться по холсту.
- **Основные элементы BPMN**:
    - **User Task (Задание пользователя)**: Прямоугольник с иконкой человечка. Это задания, которые видит пользователь в интерфейсе (Диагностика, Решение и т.д.).
    - **Start Event (Начало)**: Точка входа в процесс.
    - **End Event (Конец)**: Точка завершения процесса.
    - **Gateway (Шлюз)**: Ромб. Используется для ветвления логики. Наиболее распространенный тип — **Inclusive/Exclusive Gateway** (исключающий/включающий шлюз), позволяющий выбрать одно из нескольких направлений.
    - **Sequence Flow (Стрелка-переход)**: Соединяет элементы и определяет порядок выполнения.
    - **Call Activity**: Элемент для вызова другого бизнес-процесса.

### 4. Настройка User Task

- Тип задания (диагностика, решение и т.д.) определяется через свойство **`task-type`**.
- В панели свойств задания (вкладка **Extensions**) нужно добавить свойство `task-type` и указать соответствующий ID из таблицы `task-type`.
    - *Пример*: `task-type: 2` — это Диагностика, `task-type: 4` — это Решение.

### 5. Понятие "Rula" (Правила) и их настройка

- `Rula` (или `Rule`) — это ключевое понятие. Это переменная, которая определяет, по какой ветке пойдет процесс после завершения пользовательского задания.
- **Принцип работы**:
    1.  Пользователь завершает задание (например, "Диагностика") и выбирает результат из выпадающего списка.
    2.  В Camunda этот выбор соответствует конкретному `Rule`.
    3.  Процесс смотрит на `Rule` на стрелке, выходящей из шлюза, и, если он совпадает с выбранным пользователем, переходит по этой стрелке к следующему заданию.
- **Где настраивать**: Правило (`Rule`) **всегда** вешается на **стрелку, выходящую из шлюза (Gateway)**. Это критически важно! Стрелка до шлюза должна быть пустой.
- **Параметры Rule**:
    - Состоит из множества параметров, которые задают контекст, в котором это правило будет доступно пользователю.
    - *Примеры параметров*: Исходный тип задания (`Source Task Type`), Роль подразделения (`Source Unit Role`), Шифр закрытия (`Close Code`), Целевое подразделение (`Target Unit Role`), Макросегмент (`Macrosegment`) и т.д.
    - Если параметры пользователя/тикета не соответствуют параметрам Rule, пользователь не увидит этот результат в выпадающем списке.

### 6. Жизненный цикл токена и логика перемещения

- **Токен** — это виртуальный указатель, который движется по процессу.
- Когда пользователь завершает задание и выбирает результат, токен переходит на шлюз.
- Шлюз проверяет, какой `Rule` был выбран, и направляет токен по соответствующей стрелке к следующему заданию.
- Если токен достиг шлюза, но не соответствует ни одному из доступных `Rule` на исходящих стрелках, он "зависнет" на шлюзе, и задание не закроется.

### 7. Хранение данных о процессе в базе данных (DBeaver)

- Настройки и правила хранятся не в самом Modeller, а в базе данных.
- **Основные таблицы**:
    - **`cache.ru`**: Основная таблица для правил клиентских инцидентов (также есть `cache.o2o.ru`, `cache.network.ru`). Содержит `ID`, `external ID` (видимый в Modeller), `close_code`, `process_name`, `version` и другие основные поля.
    - **`rule.id`**: Связывает внутренний и внешний ID правила.
    - **`cache.ru.source.task.type.link`**: Связывает правило с типом исходного задания (например, `task-type: 2`).
    - **`cache.ru.source.unit.role.link`**: Связывает правило с ролью исходного подразделения.
- **Поиск правила в БД**: По `external ID` и `process name` и `version` можно найти внутренний `ID` правила, а затем через него найти все его параметры в связанных таблицах.

### 8. Вызов вложенных бизнес-процессов (Call Activity)

- **Создание**: Элемент, помеченный гаечным ключом.
- **Настройка**: В свойствах (вкладка **Extensions**) в поле **`Call Activity`** выбирается имя вызываемого процесса.
- **Переменные (Variables)**: При входе в подпроцесс и выходе из него необходимо маппить (сопоставлять) переменные.
    - **Вход**: Передаются переменные из основного процесса (например, `ticketId`, `source.unit.role`).
    - **Выход**: Передаются переменные обратно (например, `result`, `coordinator`).
    - **Важно**: Нужно правильно настроить маппинг координатора (`coordinator`) при входе и выходе. Он определяет, какая группа/подразделение станет ответственной за подпроцесс. Настройка не всегда тривиальна и зависит от конкретного процесса.
    - **Результат (`result`)**: При выходе из подпроцесса переменная `Rule` (которая использовалась внутри) маппится в переменную `result`. Именно по этим `result`-ам строится логика выхода из подпроцесса на основной процесс (см. пункт 9).

### 9. Навигация по сложным схемам и отладка

- **Фильтры**: В верхней части Modeller есть фильтры для поиска по `RuleID`, макросегменту, сегменту и т.д. Они подсвечивают нужные стрелки.
- **Поиск в Notepad**: Копируйте список `RuleID` в блокнот и ищите через `Ctrl+F`.
- **Результаты (`result`)**:
    - Когда вы заходите в подпроцесс, переменная `RuleID` внутри него должна превратиться в переменную `result` на выходе.
    - В основном процессе, на стрелках, выходящих из элемента `Call Activity`, проверяется именно **`result`**, а не `RuleID` (например, `result=14525`).
    - Чтобы найти, какая стрелка соответствует нужному `result`, нужно кликать по всем стрелкам, выходящим из `Call Activity`, и смотреть их свойства (вкладка **Extensions**). Или использовать поиск.

- **Метки**: Хорошая практика — нумеровать выходные стрелки из `Call Activity` (`result`), чтобы упростить навигацию.

### 10. Деактивация правил (Disabled Rules)

- **Визуализация**: Правила, которые временно недоступны, отображаются **розовыми/красными стрелками**.
- **Назначение**: Функционал задеплоен, но пока не должен быть доступен пользователям (например, процесс в разработке).
- **Настройка**: В свойствах стрелки (вкладка **Extensions**) добавляется свойство **`disabled`**. Сохранение схемы деактивирует это правило.

### 11. Таймеры (Timers)

- **Назначение**: Используются для управления временем выполнения задач, напоминаний или автоматических переходов при нарушении SLA.
- **Принцип работы**: Привязываются к заданию как **Boundary Event**.
- **Типы**:
    1.  **Прерывающий (Interrupting)**: Прерывает выполнение текущего задания и переводит процесс по ветке таймера.
    2.  **Непрерывающий (Non-Interrupting)**: Не прерывает задание, а создает параллельный поток (например, отправляет уведомление).
- **Настройка**: В свойствах таймера нужно указать **`Timer Definition Type`** (например, `Duration`) и **`Timer Definition`** (значение времени, например, `PT10S` — 10 секунд, `1h` — 1 час).

### 12. Управление версиями и миграция

- **Просмотр предыдущих версий**: В адресной строке браузера нужно изменить номер версии в URL (например, `.../...?version=307`).
- **Сохранение как новой версии**: Открыв старую версию и нажав "Сохранить", вы создадите новую версию (следующий номер), идентичную старой. Это можно использовать для отката.
- **Миграция** — это процесс переноса всех активных тикетов с одной версии процесса на другую.
    1.  Перейти в **`/camunda`** → **`Processes`** → **`Migration`**.
    2.  Выбрать **Source Process Key** и версию, а также **Target Process Key** и версию.
    3.  Сгенерировать запрос и нажать **`Migrate`**.
    4.  **Критично**: После миграции необходимо вручную (или через `UPDATE`-запрос в БД) обновить версию процесса для соответствующих тикетов в таблице `tasks` (поля `process_name` и `process_version`).
    5.  **Предупреждение**: Если REST API на `/camunda` недоступно (`Unknown`), активация его может привести к падению всего сервиса. Делайте это только вместе с разработчиком.

### 13. Красные стрелки и их причины

- **Причины**:
    1.  Указанный на стрелке `RuleID` не существует в базе данных для данной версии процесса.
    2.  Произошел баг при сохранении схемы (новые правила не создались).
    3.  Правило было удалено из базы данных вручную.
- **Диагностика**: Через DBeaver проверить, существует ли правило в `cache.ru` по `external ID` и `process_name`/`version`.
- **Восстановление**:
    1.  Найти, на каких версиях правило существовало раньше (поиск без фильтра по версии).
    2.  Скопировать запись для нужной версии из старой схемы.
    3.  Вставить в `cache.ru`, поменяв `version` и удалив `id` (он сгенерируется автоматически).
    4.  Восстановить связи в таблицах `source.task.type.link`, `target.task.type.link`, `source.unit.role.link` и др., используя новый сгенерированный `id`.
    5.  Обновить страницу — стрелка должна стать черной.

## Часть 2: Диагностика и устранение ошибок

### 1. Основные кейсы неисправностей

1.  **Тикет пошел не по той ветке**: Ожидали один результат, получили другой.
2.  **У пользователя не отображаются результаты задания (пустой список)**.
3.  **Пользователь не может закрыть задание (зависло на шлюзе)**.
4.  **Тикеты в тупике (отсутствуют исходящие стрелки)**.

### 2. Диагностика пути тикета

- **По цветам в интерфейсе TTM**: Каждый процесс имеет свой цвет (например, основной процесс — желтый, ожидание — синий). В фильтре можно посмотреть соответствие цвета и процесса.
- **По базе данных**: Таблица `tasks`. Поля `process_name` и `process_version` показывают текущий процесс и его версию.

### 3. Диагностика через Camunda Admin (Админка)

- **URL**: `http://<ip>:880/app/cockpit/default/` (логин/пароль: `admin`/`admin`).
- **Поиск тикета**: В разделе **`Processes`** → выбрать процесс → `Add Criteria` → `Business Key` → ввести номер инцидента.
- **Просмотр состояния**: Нажав на процесс, можно увидеть все его активные элементы и текущее местоположение токена.
- **Визуализация связей**: В админке видно, где находится токен. Имея `ID` родительского задания (`Parent Task ID`), можно проследить путь тикета.

### 4. Проблема: "Нет результатов у задания" (Пустой список Rule)

- **Причина**: Параметры тикета (роль подразделения, вид услуги, тип проблемы и т.д.) не соответствуют параметрам, заданным в `Rule` на схеме.
- **Диагностика**: Использовать инструменты разработчика в браузере (`F12`). Во вкладке **Network** посмотреть ответ на запрос `/rules`. В ответе можно увидеть, какие правила были найдены и почему (например, `unitRole` не совпадает).
- **Быстрое решение**:
    1.  В интерфейсе TTM изменить параметры тикета вручную (например, сменить роль подразделения в левой панели инцидента) на те, которые соответствуют правилам.
    2.  После изменения обновить страницу, и результаты должны появиться.
- **Важно**: Если проблема массовая, нужно разбираться с настройками процесса, а не править тикеты вручную.

### 5. Проблема: "Тикет в тупике" (Нет исходящих стрелок)

- **Причина**: Токен оказался на шлюзе или задании, у которого нет ни одной исходящей стрелки с подходящим правилом.
- **Решение**:
    1.  Понять, на каком элементе находится токен (через админку Camunda).
    2.  В Modeller найти этот элемент и посмотреть, есть ли у него исходящие стрелки и какие `Rule` или `result` на них висят.
    3.  Если стрелок вообще нет — добавить новую стрелку с новым `Rule` и настроить его в БД.
    4.  Если они есть, но не соответствуют контексту тикета — изменить параметры тикета вручную (как в п. 4) или мигрировать тикет на другую версию процесса.

### 6. Общий план действий при ошибке

1.  **Определить** проблему (что ожидалось, что произошло).
2.  **Найти** местоположение тикета (в админке Camunda).
3.  **Проверить** настройки в Camunda Modeller на соответствующей версии.
4.  **Проверить** существование и корректность `Rule` в базе данных через DBeaver.
5.  Применить одно из решений:
    - Вручную поправить параметры тикета (временное решение).
    - Добавить/восстановить недостающие правила в БД.
    - Создать новую версию процесса и мигрировать на нее.
    - Откатить на предыдущую версию.

## Заключение и рекомендации

- **Лучший способ обучения**: Практика. Можно запросить отдельную "песочницу" (схему) для экспериментов, не боясь сломать основные процессы.
- **Самый эффективный способ настройки**: Держать рядом два экрана/вкладки: один с эталонной схемой (на другом стенде), второй с той, которую настраиваете, и просто копировать все параметры.
- **Связь с разработчиками**: Все сложные технические изменения (активация REST API для миграции, проблемы с интеграциями) следует обсуждать с командой разработки.
- **Обратная связь**: По итогам обучения будет отправлена форма обратной связи, а также ссылки на записи и полезные статьи в Confluence.

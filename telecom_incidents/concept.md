# 📋 Концепция пет-проекта: "Система управления инцидентами телеком-оператора" (TTM Lite)

## 🎯 Цель проекта

Разработать упрощенную версию системы управления инцидентами (Trouble Ticket Management) для телеком-оператора, демонстрирующую ключевые компетенции системного аналитика:
- Моделирование бизнес-процессов в BPMN
- Проектирование структуры данных
- Документирование API
- Настройка бизнес-правил и маршрутизации

## 📖 Бизнес-контекст

В телеком-компаниях существует процесс обработки инцидентов клиентов:

1. **Создание инцидента** — клиент сообщает о проблеме (отсутствие интернета, проблемы с VPN, качество связи)
2. **Диагностика** — специалист 1-й линии (1LTP) проводит первичную проверку
3. **Решение** — если проблема сложная, передается на 2-ю линию (2LTP)
4. **Подтверждение** — клиент подтверждает устранение проблемы
5. **Закрытие** — инцидент закрывается с фиксацией результата

## 🧩 Ключевые элементы системы (на основе реального TTM)

### 1. Бизнес-процессы
Процессы, управляющие потоком работ:
- **Основной процесс** (`ttm_rule2`) — главный маршрут обработки инцидента
- **Блок решения МРФ** (`ttm_solve_mrf`) — процесс принятия решения на уровне макрорегионального филиала
- **Ожидание** (`waiting`) — ожидание внешних событий или ответа клиента
- **Таймеры SLA** (`timers`) — контроль соблюдения сроков

### 2. Типы заданий (User Tasks)
Каждое задание имеет свой тип, определяющий его поведение:
- `task-type: 2` — Диагностика
- `task-type: 3` — Ожидание
- `task-type: 4` — Решение
- `task-type: 6` — Подтверждение клиентом
- `task-type: 7` — Проверка

### 3. Правила маршрутизации (Rules)
Определяют переход между заданиями:
- **`RuleID`** — уникальный идентификатор правила
- **Параметры правила**: исходный тип задания, целевое подразделение, роль, контекстные условия (сегмент клиента, тип услуги)
- **Результаты (`result`)** — переменные на выходе из подпроцессов

### 4. Роли и подразделения
- **1LTP** — первая линия технической поддержки
- **2LTP** — вторая линия технической поддержки
- **МРФ** — макрорегиональный филиал
- **ГРПЦ** — группа регионального проектирования и консалтинга

### 5. Атрибуты инцидента
- **№ инцидента** — уникальный идентификатор
- **Клиент** — наименование организации
- **Услуга клиента** — тип услуги (Интернет, VPN, Wi-Fi Hotspot, OTT)
- **Тип проблемы** — Клиентская, Сетевая
- **Приоритет** — от 1 (критичный) до 8 (низкий)
- **SLA** — допустимое время решения
- **Статус** — Создан, В работе, На подтверждении, Закрыт
- **Макросегмент/Сегмент** — категоризация клиентов (B2B, B2G, B2C)
- **МФУ Клиента** — подразделение, ответственное за клиента
- **Адрес** — местонахождение клиента

### Структура базы данных (основные таблицы)

```sql
-- Правила маршрутизации
CREATE TABLE cache_rule (
    id INT PRIMARY KEY AUTO_INCREMENT,
    external_id INT,
    process_name VARCHAR(255),
    process_version INT,
    close_code VARCHAR(50),
    target_unit_role VARCHAR(100)
);

-- Связи правил с типами заданий
CREATE TABLE rule_source_task_type_link (
    rule_id INT,
    task_type_id INT
);

-- Инциденты
CREATE TABLE incident (
    id INT PRIMARY KEY,
    number VARCHAR(20),
    client_name VARCHAR(255),
    service_type VARCHAR(50),
    problem_type VARCHAR(50),
    priority INT,
    status VARCHAR(50),
    macro_segment VARCHAR(10),
    segment VARCHAR(10),
    sla_time VARCHAR(20),
    mfu_client VARCHAR(100),
    address TEXT,
    cms_order_number VARCHAR(20),
    created_date TIMESTAMP
);

-- Задания
CREATE TABLE tasks (
    id INT PRIMARY KEY,
    incident_id INT,
    task_type INT,
    unit_role VARCHAR(100),
    status VARCHAR(50),
    created_date TIMESTAMP,
    started_date TIMESTAMP,
    closed_date TIMESTAMP,
    result VARCHAR(255)
);
```

## 📊 Модель процесса в BPMN

### Основной процесс (упрощенный)

```
[Start] → [Диагностика 1LTP] → [Шлюз]
                                 ├─→ [Решение] → [Подтверждение клиента] → [End]
                                 ├─→ [Диагностика 2LTP] → [Решение МРФ] → [Шлюз2]
                                 │                                          ├─→ [Подтверждение] → [End]
                                 │                                          └─→ [Ожидание] → [Врап]
                                 └─→ [Ожидание внешнего события] → [Диагностика]
```

### Пример правила (Rule)

```json
{
    "RuleID": 14525,
    "SourceTaskType": 2,  // Диагностика
    "TargetTaskType": 4,  // Решение
    "SourceUnitRole": "1LTP",
    "TargetUnitRole": "МРФ",
    "Macrosegment": "B2B",
    "ServiceType": "VPN L2/L3",
    "CloseCode": "REQUIRES_CHECK"
}
```

## 🔧 Технические требования

### REST API (OpenAPI 3.0)

```yaml
openapi: 3.0.0
paths:
  /api/incidents:
    get:
      summary: Получить список инцидентов
    post:
      summary: Создать новый инцидент
  /api/incidents/{id}:
    get:
      summary: Получить детали инцидента
  /api/tasks/{id}/complete:
    post:
      summary: Завершить задание
      requestBody:
        content:
          application/json:
            schema:
              type: object
              properties:
                result: string
  /api/rules:
    get:
      summary: Получить правила для текущего задания
```

### Пример BPMN-процесса (Camunda)

```xml
<?xml version="1.0" encoding="UTF-8"?>
<definitions xmlns="http://www.omg.org/spec/BPMN/20100524/MODEL">
    <process id="ttm_rule2" name="Основной процесс" isExecutable="true">
        <startEvent id="start" name="Начало процесса" />
        
        <userTask id="diagnostics" name="Диагностика">
            <extensionElements>
                <camunda:properties>
                    <camunda:property name="task-type" value="2" />
                </camunda:properties>
            </extensionElements>
        </userTask>
        
        <exclusiveGateway id="gateway1" name="Выбор маршрута" />
        
        <userTask id="solution" name="Решение">
            <extensionElements>
                <camunda:properties>
                    <camunda:property name="task-type" value="4" />
                </camunda:properties>
            </extensionElements>
        </userTask>
        
        <sequenceFlow id="flow1" sourceRef="start" targetRef="diagnostics" />
        <sequenceFlow id="flow2" sourceRef="diagnostics" targetRef="gateway1" />
        
        <sequenceFlow id="flow3" sourceRef="gateway1" targetRef="solution">
            <extensionElements>
                <camunda:properties>
                    <camunda:property name="ruleId" value="14525" />
                </camunda:properties>
            </extensionElements>
        </sequenceFlow>
        
        <endEvent id="end" name="Конец процесса" />
        <sequenceFlow id="flow_end" sourceRef="solution" targetRef="end" />
    </process>
</definitions>
```
